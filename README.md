# clouds-messenger-mcp

MCP-сервер для корпоративного мессенджера Clouds (белая сборка eXpress). Даёт агенту читать переписку, искать по чатам и контактам, читать треды, реакции и опросы, скачивать вложения и отправлять текст от вашего имени.

Это личный неофициальный инструмент. Публичного API у платформы нет: протокол снят реверсом веб-клиента, работа идёт на той же сессии, что и у браузера. Playwright один раз поднимает персистентный профиль и снимает с него сессию, дальше протокол (Phoenix WebSocket и REST) гоняется в Node без браузера. Отсюда раздел [Ограничения и пробелы в доказательствах](#ограничения-и-пробелы-в-доказательствах) внизу: его стоит прочитать до того, как полагаться на инструмент.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `list_chats` | Список чатов со счётчиком непрочитанного, свежие первыми |
| `get_history` | Страница переписки чата: курсором либо окном по датам |
| `get_message` | Одно сообщение по паре чат и `message_id`, без загрузки истории |
| `get_message_context` | Окно вокруг сообщения: N сообщений до и N после |
| `search` | Поиск чатов по имени и людей по контактам |
| `get_thread` | Сообщения треда по `thread_id` либо по стартовому сообщению |
| `get_poll` | Опрос, приложенный к сообщению: сырые поля без нормализации |
| `list_reactions` | Реакции сообщения со счётчиками и пометкой своих |
| `download_attachment` | Скачивает вложение на диск и отдаёт абсолютный путь |
| `send_message` | Отправка текста. Двухшаговая: draft, затем confirm |

Отказы у всех инструментов предметные, а не MCP-ошибки: наружу уезжает `status` с полями `reason` и `next_step`, по которым вызывающий ветвится сам. Ненайденный чат, неоднозначное имя, отсутствующее сообщение и неприменимая операция это факты переписки, а не сбои сервера.

Форму, снятую не с живого провода, инструменты объявляют полем `form_status` со значением `bundle` (форма взята из бандла веб-клиента) либо `unconfirmed` (форма живой пробой не наблюдалась), и полем `form_note` с причиной. Обещание одно: неполнота объявлена в самой выдаче, а не спрятана.

Адресация чата у всех инструментов одинакова: в поле `chat` идёт либо идентификатор (UUID), либо запрос по имени. Чат с собой резолвится по именам «Избранное», «Заметки», `notes`, `saved messages`, «себе», «я», `me`. Резолв не гадает: на нескольких совпадениях уезжает `status:"ambiguous_chat"` со списком кандидатов. Резолв всегда стоит одного обращения за списком чатов, и в цене каждого инструмента ниже он учтён.

### `list_chats`

Точка входа: единственный инструмент, которому не нужен заранее известный идентификатор.

| Параметр | Тип | По умолчанию |
|---|---|---|
| `limit` | целое 1-500 | 50 |
| `unread_only` | bool | false |
| `include_last_message_text` | bool | false |

Ответ: `{status:"ok", chats[], total_chats, unread_chats}`. У чата: `chat_id`, `name`, `kind` (`notes`, `chat`, `group_chat`, `channel`, `botx`, `global`, `voex_call`), `members_count`, `last_activity`, `unread_count`, `unread`, `pinned_message_id`. `total_chats` это число чатов ДО фильтрации и среза: сравнение с длиной `chats` показывает срез.

Цена: два обращения к серверу (список чатов и счётчики непрочитанного). Счётчики приезжают отдельным событием, а не полем чата, поэтому свести их к одному обращению нельзя. Опт-ин `include_last_message_text:true` стоит ЕЩЁ ПО ОДНОМУ обращению на каждый чат страницы и добавляет к чату ключ `last_message` с текстом.

Текст последних сообщений по умолчанию не отдаётся намеренно: иначе один вызов утаскивал бы в контекст модели содержимое всех переписок сразу.

Подтверждено живьём: полный список чатов и счётчики непрочитанного. `form_status` в выдаче не появляется.

### `get_history`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | UUID либо запрос по имени | обязателен |
| `limit` | целое 1-200 | 50 |
| `before` | курсор: `message_id` (UUID), исключающий | нет |
| `from_date` | ISO, нижняя ВКЛЮЧАЮЩАЯ граница | нет |
| `to_date` | ISO, верхняя ИСКЛЮЧАЮЩАЯ граница | нет |
| `after` | ISO, строго ПОСЛЕ метки, альтернатива `from_date` | нет |

Ответ: `{status:"ok", chat_id, messages[], next_before?, has_more?}`. Пагинация: взять `next_before` из выдачи и передать его в `before` следующего вызова. Курсор исключающий: сообщение с этим идентификатором в выдачу не попадает.

Поле сообщения: `message_id` (UUID, он же `sync_id` события), `chat_id`, `from`, `timestamp` (ISO), `event_type` (тип внешнего события), `type` (тип внутреннего события: `text`, `image`, `file`), `text`, `attachments[]`, `reactions[]`, `read_by_count`, `decrypt_error`. Обогащение чатом добавляет `chat_name`, `chat_kind`, `is_self_chat`. Отсутствующее поле означает «этого в событии не было»: выдуманная метка времени хуже отсутствующей, потому что по ней отфильтруют и отсортируют.

Не расшифровавшееся сообщение остаётся в выдаче с полем `decrypt_error`, а не выпадает из неё молча.

Цена: резолв чата плюс одна страница истории. С фильтрами по датам страницы добираются на стороне сервера MCP, до двадцати штук за вызов: серверных временных границ в истории нет.

Подтверждено живьём: чтение истории назад с лимитом и курсором, расшифровка событий, порядок элементов страницы у сервера (от новых к старым; страница всё равно сортируется здесь по времени вставки, потому что порядок сервером не обещан), включающая семантика курсора на проводе (наружу объявлена исключающая: событие курсора выбрасывается явно) и признак продолжения. Сервер присылает его полем `has_more_events`, и это и есть `has_more` в выдаче. Ключ появляется ТОЛЬКО из ответа сервера: если сервер промолчал, ключа нет, а обход продолжается по `next_before` до пустой страницы.

### `get_message`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | UUID либо запрос по имени | обязателен |
| `message_id` | UUID из выдачи `get_history` | обязателен |

Ответ: `{status:"ok", chat_id, message}` либо `{status:"message_not_found", reason, next_step}`. Отсутствие сообщения это не ошибка: сообщение могло быть удалено, и это штатный факт переписки.

Цена: резолв чата плюс адресное чтение события. Если адресное чтение сервером не поддержано либо ничего не дало, сообщение ищется проходом по истории, и это стоит дополнительных страниц.

Путь адресного чтения подтверждён живой пробой: сервер принимает адресное событие и отвечает конвертом с полем `info`, из которого сообщение читается и расшифровывается. Меток неподтверждённости выдача поэтому не несёт, а запасной проход по истории остаётся на случай, если сервер на адресное чтение не ответит.

### `get_message_context`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | UUID либо запрос по имени | обязателен |
| `message_id` | UUID в центре окна | обязателен |
| `before_count` | целое 0-200 | 10 |
| `after_count` | целое 0-200 | 10 |

Ответ: `{status:"ok", chat_id, pivot_message_id, before[], message?, after[]}`. Списки идут от старых к новым. Ключ `message` отсутствует, если самого сообщения уже нет: окна вокруг при этом целы, потому что строятся границами, а не от найденного события.

Цена: резолв чата плюс до трёх обращений за событиями (само сообщение, страница до, страница после).

Отдельного события «контекст» на проводе нет: сторона «до» это обычная страница назад от адреса, сторона «после» та же страница с направлением вперёд. Направление вперёд подтверждено живой пробой (окно «после» на полигоне непустое), поэтому меток неподтверждённости выдача не несёт.

### `search`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `query` | подстрока имени, регистр не важен | обязателен |
| `entities` | массив из `users`, `chats`, `messages` | `["users","chats"]` |
| `limit` | целое 1-200, максимум в КАЖДОЙ выдаче | 50 |

Ответ: `{status:"ok", query, chats?[], users?[], escalation?, truncated, partial?, partial_reason?}`. Флаг `truncated` поднимается, если хоть одна выдача упёрлась в `limit`: неполнота видна, а не угадывается.

Цена: одно обращение за списком чатов; с `entities` включающими `chats` ещё одно за счётчиками непрочитанного.

Ищет ПО СПИСКУ ЧАТОВ, а не на сервере: серверной ручки поиска у платформы не снято ни живой пробой, ни с бандла. Люди находятся только среди контактов, с которыми уже есть личный чат, поэтому выдача `users` всегда помечается `partial:true` с причиной в `partial_reason`.

Поиска по текстам сообщений платформа не даёт. Запрос `entities:["messages"]` возвращает не пустую выдачу, а `escalation` с причиной и следующим шагом: пустая выдача читалась бы агентом как факт «ничего не найдено», то есть как утверждение о переписке, которого никто не проверял. Следующий шаг это `get_history` с фильтрами дат.

### `get_thread`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | родительский чат: UUID либо запрос по имени | обязателен |
| `thread_id` | UUID треда, если он известен | нет |
| `message_id` | UUID сообщения, от которого начат тред | нет |
| `limit` | целое 1-200 | 40 |
| `before` | курсор: `message_id` (UUID) | нет |

Передавать нужно ровно одно из `thread_id` и `message_id`, иначе уезжает `{status:"invalid_input", reason, next_step}`. Ответ: `{status:"ok", thread_id, chat_id, empty, messages[], next_before?, has_more?}` либо `{status:"thread_not_found", reason, next_step}`.

Флаг `empty:true` означает «событий не отдано». Это либо тред, ещё не материализованный сообщением, либо конец обхода, если был передан `before`: различить их может только вызывающий по курсору.

Цена: три обращения к серверу (список чатов, список тредов, страница треда).

Подтверждено живьём: элемент списка тредов и история треда. Не подтверждено: равенство адреса треда и адреса стартового сообщения (взято из бандла), поэтому вызов по `message_id` несёт `form_status:"bundle"`, а существование треда дополнительно проверяется по списку. Сужение списка тредов по чату сервер ИГНОРИРУЕТ (живая проба: на суженный запрос приезжают треды всех чатов), поэтому принадлежность чату проверяется локально. Страница треда живьём в этой итерации не читалась, поэтому при отсутствии `has_more` в ответе выдача по-прежнему несёт `form_status:"unconfirmed"`.

### `get_poll`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | групповой чат: UUID либо запрос по имени | обязателен |
| `message_id` | UUID сообщения, к которому приложен опрос | обязателен |

Ответ: `{status:"ok", chat_id, message_id, poll_id?, poll, my_votes?, form_status:"unconfirmed", form_note}`. Поле `poll` это СЫРЫЕ поля опроса без нормализации: раскладывать по своим именам форму, которую никто не видел живьём, значит закрепить догадку и потерять всё, что в неё не попало. Адрес `poll_id` разбирается отдельно, потому что им адресуется голосование, и это НЕ `message_id`.

Отказы: `{status:"not_a_poll", reason, form_status:"unconfirmed", form_note}` и `{status:"not_applicable", reason, next_step}`. Второй приходит в личном чате и в заметках: опрос это функция группового чата.

Цена: резолв чата плюс чтение события.

Форма НЕ подтверждена живьём ни в одном исходе, включая отрицательный. Опрос нельзя завести в чате с собой, а полигон живых проб это именно чат с собой, поэтому и признак опроса, и состав полей взяты из бандла веб-клиента. Отдельной серверной ручки чтения опроса нет: опрос приезжает внутри сообщения, а счётчики голосов приходят отдельными событиями и в этой выдаче не видны.

### `list_reactions`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | UUID либо запрос по имени | обязателен |
| `message_id` | UUID из выдачи `get_history` | обязателен |

Ответ: `{status:"ok", chat_id, message_id, reactions[], total}`. Элемент: `{emoji, count, mine}`. Поле `total` это сумма счётчиков.

Реакция здесь это САМ ЭМОДЗИ (строка Unicode), а не числовой идентификатор артворка: значение из выдачи годится для показа человеку как есть.

Цена: резолв чата плюс чтение события.

И форма реакций, и оба пути чтения события подтверждены живьём, поэтому меток неподтверждённости выдача не несёт: реакции одинаковы независимо от того, каким путём нашлось событие.

### `download_attachment`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | UUID либо запрос по имени | обязателен |
| `message_id` | UUID сообщения с вложением | обязателен |
| `file_id` | какое вложение скачивать | первое вложение сообщения |

Ответ: `{status:"ok", path, file_name, size, mime_type?, encrypted?, form_status:"unconfirmed", form_note}` либо `{status:"file_not_found", reason, next_step}`. Значение `file_id` берётся из поля `attachments` прочитанного сообщения.

Единственный инструмент набора, который пишет на диск, поэтому он не помечен read-only. Повтор не идемпотентен: он кладёт рядом ещё одну копию, а не затирает прежнюю. Скачанные файлы удаляются автоматически, см. [Автоочистка загрузок](#автоочистка-загрузок-ttl).

Цена: резолв чата, чтение события и сама загрузка.

Форма НЕ подтверждена живьём: адрес файловой службы и параметр `key_id` взяты из бандла веб-клиента, а потоковый шифр с файла не снимается, потому что разметка потока живой пробой не проверялась. У зашифрованного вложения в ответе стоит `encrypted:true`, и на диске лежит шифротекст ровно таким, каким его отдал сервер.

### `send_message`

| Параметр | Тип | По умолчанию |
|---|---|---|
| `chat` | UUID либо запрос по имени | обязателен |
| `text` | строка 1-10000 символов | обязателен |
| `confirm` | bool: подтвердить отправку | false |
| `confirm_token` | токен из выдачи шага draft | нет |

Отправка двухшаговая, подробности и пример в разделе [Confirm-политика](#confirm-политика).

Шаг draft отдаёт `{status:"draft", chat_id, chat_name?, text_preview, confirm_token, next_step}`; в сокет при этом не уходит ничего. Поле `text_preview` это первые 200 символов, они нужны человеку для чтения, а предметом отпечатка является текст целиком. Шаг confirm отдаёт `{status:"sent", chat_id, message_id, inserted_at?}`, где `message_id` это клиентский идентификатор отправки, он же адрес сообщения в истории; метка `inserted_at` появляется, только если её прислал сервер. Отказ подтверждения: `{status:"confirm_rejected", reason, next_step}` с причиной `missing_token`, `malformed_token`, `op_mismatch`, `chat_mismatch` либо `fingerprint_mismatch`. Неоднозначный чат отправку блокирует: наружу уходят кандидаты, отправка не идёт.

Цена: резолв чата на каждом шаге, обращение за ключами получателей и одно обращение отправки.

Упоминания (`@mentions`) НЕ поддерживаются: форма упоминания во внутреннем событии платформы не снята, и подставлять её наугад значило бы отправить в чат текст неизвестного вида.

Подтверждено живьём: полный round-trip отправки текста в чат с собой, включая обёртку контент-ключа на ключи получателей чата и подпись. Не установлено: серверный дедуп по повторному `sync_id`. Повторный confirm с тем же токеном отдаёт запомненный результат из локальной памяти процесса, и это единственная гарантия: серверный дедуп здесь не обещается, а после перезапуска сервера локальная память пуста.

## Треды

Тред это чат: у него собственный идентификатор, читается он теми же страницами и той же формой сообщений, что и обычный чат.

- **Чтение:** `get_thread` открывает тред по готовому `thread_id` либо по паре `chat` и `message_id` стартового сообщения. Пагинация та же, что у `get_history`: `limit` и курсор `before`, значение для следующей страницы это `next_before` из выдачи.
- **Отправка в тред** идёт обычным `send_message`, где в поле `chat` передан `thread_id`.
- **Адрес треда выводится, а не запрашивается.** Равенство адреса треда и адреса стартового сообщения снято с бандла веб-клиента и живой пробой не подтверждено, поэтому вызов по `message_id` дополнительно проверяет существование треда по списку тредов и несёт `form_status:"bundle"`.
- **Подписка на тред и выход из него** в первой версии не реализованы, см. [Чего нет по решению](#чего-нет-по-решению-отложено).

## Требования

- Node.js >= 22
- Chromium для Playwright: `npx playwright install chromium`
- Учётная запись Clouds с доступом к веб-клиенту

## Установка

### Через npx

Отдельно устанавливать пакет не нужно: `npx` скачивает его из реестра по требованию. Разово нужен только браузерный движок, которым сервер управляет при входе:

```bash
npx playwright install chromium
```

Дальше сервер запускает MCP-клиент командой `npx clouds-messenger-mcp`, см. [Подключение к MCP-клиенту](#подключение-к-mcp-клиенту). Руками её запускать не требуется.

### Из исходников

```bash
git clone https://github.com/conarti/clouds-messenger-mcp.git
cd clouds-messenger-mcp
npm ci
npx playwright install chromium
npm run build
```

Скрипты сборки, тестов и проверки типов в разделе [Разработка](#разработка).

## Первый запуск и авторизация

Отдельного шага логина нет: авторизация ленивая и случается на первом вызове инструмента, который реально идёт к серверу. Список инструментов отвечает и без сессии.

1. **Первый вызов.** Поднимается Chromium с персистентным профилем (`~/.config/clouds-messenger-mcp/profile/`). Сначала headless, с бюджетом 30 секунд: если в профиле уже есть живая сессия, вход проходит незаметно.
2. **Ручной вход.** Не уложились в headless-бюджет, значит окно поднимается видимым, и на ручной вход даётся до 5 минут. Войдите обычным способом.
3. **Снятие сессии.** Сервер ждёт, пока приложение отработает стартовое обновление токена, и только после этого снимает свежий токен, набор cookie, параметры сокета и ключевой материал из профиля. Браузер после этого закрывается: весь протокол дальше идёт в Node.
4. **Последующие запуски** работают на сохранённом профиле, ручной вход не требуется.
5. **Протухание.** При отказе по авторизации (401 на REST либо отказ сокета) профиль поднимается заново, и приложение само обновляет токен. Если и это не помогло, окно поднимется видимым и вас попросят войти руками.

Обновление токена только реактивное. Читаемого срока жизни у токена нет: он непрозрачный, и время истечения из него не достаётся, поэтому проактивного обновления по таймеру сервер не делает, а реагирует на отказ.

> Профиль и загрузки это ваши личные данные. Каталог `~/.config/clouds-messenger-mcp/` содержит живую сессию мессенджера: он не должен попадать в git, в синхронизацию или в бэкапы, из которых его кто-то достанет.

## Конфигурация

Три источника, приоритет по возрастанию: **дефолты, файл, программный аргумент**. Слияние поточечное внутри секции: частичный файл не обнуляет соседние поля.

Файл: `~/.config/clouds-messenger-mcp/config.json`. Целиком опционален, без него всё работает на дефолтах. Путь до файла переопределяется переменной окружения `CLOUDS_MESSENGER_MCP_CONFIG`. Поле `paths.configFile` отчитывается о фактически прочитанном файле, и содержимое самого файла это значение переписать не вправе.

Пути в секции `paths` обязаны быть абсолютными: относительный путь загрузчик не резолвит.

| Ключ | Дефолт | Смысл |
|---|---|---|
| `protocol.webOrigin` | `https://clouds.org.ru` | Origin веб-клиента: туда заходит браузер при входе |
| `protocol.restBaseUrl` | `https://cts01.clouds.org.ru/api` | База REST без завершающего слеша |
| `protocol.wsUrl` | `wss://cts01.clouds.org.ru/socket/user/websocket` | Сокет без query |
| `protocol.wsVsn` | `1.0.0` | Значение query `vsn` в хендшейке |
| `protocol.wsVersion` | `6` | Значение query `version` сокета |
| `protocol.chatListRequestVersion` | `6` | Версия схемы события списка чатов |
| `protocol.threadListRequestVersion` | `2` | Версия схемы события списка тредов |
| `protocol.kdcKeysPath` | `/v1/kdc/keys/` | Путь службы ключей относительно `restBaseUrl` |
| `protocol.fileServicePath` | `/v2/file_service/files/groupchat_file/` | Путь файловой службы относительно `restBaseUrl` |
| `protocol.userAgent` | строка Chrome | Без узнаваемого браузерного значения сервер отвечает отказом |
| `paths.configFile` | `~/.config/clouds-messenger-mcp/config.json` | Информационное поле: фактически прочитанный файл |
| `paths.profileDir` | `~/.config/clouds-messenger-mcp/profile` | Персистентный профиль браузера: там сессия и ключевой материал |
| `paths.downloadsDir` | `~/.config/clouds-messenger-mcp/downloads` | Каталог скачанных вложений |
| `downloads.ttlDays` | `7` | TTL автоочистки загрузок. Значение не больше нуля ВЫКЛЮЧАЕТ подметание |
| `downloads.maxFileSizeBytes` | `268435456` | Потолок размера одного скачиваемого файла (256 МиБ) |
| `limits.listChatsDefaultLimit` | `50` | Дефолтный `limit` для `list_chats` |
| `limits.searchDefaultLimit` | `50` | Дефолтный `limit` для `search` |
| `limits.historyDefaultLimit` | `50` | Дефолтный `limit` для `get_history` |
| `auth.headlessTimeoutMs` | `30000` | Бюджет headless-входа: не уложились, поднимается видимое окно |
| `auth.headedTimeoutMs` | `300000` | Бюджет ручного входа в видимом окне |
| `ws.authenticateTimeoutMs` | `10000` | Ожидание ответа на авторизацию сокета |
| `ws.authenticateAttempts` | `2` | Попытки авторизации сокета. Значение больше единицы не запас на будущее: первый кадр живьём иногда остаётся без ответа |
| `ws.requestTimeoutMs` | `30000` | Ожидание ответа на обычный запрос |
| `ws.reconnectAttempts` | `5` | Попытки переподключения |
| `ws.reconnectBaseDelayMs` | `500` | Стартовая пауза переподключения |
| `ws.reconnectMaxDelayMs` | `10000` | Потолок паузы переподключения |
| `ws.heartbeatIntervalMs` | `30000` | Период служебного кадра поддержания сокета |

Секция `protocol` существует ради устойчивости к ротации: хосты и версии протокола дрейфуют вместе с релизами веб-клиента, и перевыпускать пакет ради смены номера версии запроса дороже, чем позволить переопределить значение файлом.

Уровень логов задаётся переменной `CLOUDS_MESSENGER_MCP_LOG_LEVEL` (`debug`, `info`, `warn`, `error`; по умолчанию `info`). Лог идёт в **stderr** строками JSON: stdout принадлежит stdio-транспорту MCP, и любой посторонний байт там делает поток неразбираемым. В логе редактируются и секреты сессии, и содержимое переписки: редакция идёт и по именам полей, и по значениям, потому что секрет часто приезжает не отдельным полем, а внутри строки.

## Автоочистка загрузок (TTL)

Скачанное вложение это копия чужой переписки на диске, и она не должна жить вечно только потому, что агент один раз её открыл.

- **Что удаляется:** обычные файлы в каталоге загрузок, у которых время изменения старше TTL (по умолчанию 7 дней). Строго старше: файл ровно на границе остаётся.
- **Когда:** на старте сервера И перед каждым скачиванием. Второе важнее первого: сервер может неделями не перезапускаться, и старт как единственная точка очистки не сработал бы ни разу.
- **Границы:** корень каталога загрузок и каталоги первого уровня (загрузки разложены по чатам). Глубже подметание не спускается и по символическим ссылкам не ходит: ссылка в этой папке указывала бы наружу, а за её пределы очистка права выходить не имеет.
- **Отказ на одном файле не прекращает проход:** из-за одного занятого файла остальные протухшие копии оставаться на диске не должны.
- **Выключить:** `downloads.ttlDays: 0`. Это именно «не подметать», а не «удалить всё разом».

## Confirm-политика

Подтверждение (draft, затем confirm) стоит только у необратимых операций. В первой версии необратимая операция ровно одна: `send_message`. Отправленное сообщение уходит живому собеседнику, и отменить его тем же инструментом за один вызов нельзя.

Всё остальное в наборе это чтение, и подтверждения не требует. Дешёвый confirm обесценивает дорогой: если подтверждать приходится и безобидное чтение, кнопку начинают жать не глядя.

### Двухшаговая отправка

**Шаг 1, draft.** Обычный вызов резолвит чат и возвращает превью. В сокет не уходит ничего.

```json
{
  "status": "draft",
  "chat_id": "00000000-0000-0000-0000-000000000000",
  "chat_name": "Избранное",
  "text_preview": "первые символы текста",
  "confirm_token": "...",
  "next_step": "Ничего не отправлено. Повторите вызов с confirm:true, тем же confirm_token и неизменёнными chat и text"
}
```

**Шаг 2, confirm.** Повторный вызов с `confirm:true`, тем же `confirm_token` и НЕИЗМЕНЁННЫМИ `chat` и `text`:

```json
{
  "status": "sent",
  "chat_id": "00000000-0000-0000-0000-000000000000",
  "message_id": "11111111-1111-1111-1111-111111111111",
  "inserted_at": "2026-09-08T10:15:00.000Z"
}
```

Почему на confirm идёт повторная сверка, а не «отправить то, что в токене»: между шагами может смениться всё. Тот же запрос `chat` завтра резолвится в другой чат, потому что появился однофамилец или кто-то переименовался. Или к старому токену подставили другой текст. Поэтому токен несёт резолвнутый адрес чата и отпечаток текста, на confirm чат резолвится и текст хэшируется заново, и результаты сверяются. Расхождение это отказ, а не отправка наиболее вероятного.

Причины отказа `confirm_rejected`:

| `reason` | Что случилось |
|---|---|
| `missing_token` | Передан `confirm:true`, но `confirm_token` не приложен |
| `malformed_token` | Токен нечитаем: не разбирается либо не несёт ожидаемых частей |
| `op_mismatch` | Токен выдан другой операцией: перепутать драфты нельзя |
| `chat_mismatch` | Запрос `chat` резолвится не в тот чат, для которого выдан токен |
| `fingerprint_mismatch` | Текст изменился между draft и confirm |

Токен намеренно не подписан: подделывать его бессмысленно. Он не полномочие, а память о драфте, потому что отправка всё равно идёт в заново проверенный чат.

Повторный confirm с уже израсходованным токеном возвращает запомненный результат, и второй отправки не происходит. Запоминается ТОЛЬКО удавшаяся отправка: отказ сервера мимо памяти проходит намеренно, иначе повтор возвращал бы неудачу и лишал вызывающего единственного законного способа переотправить сообщение тем же токеном.

Память эта локальная и живёт в процессе: после перезапуска сервера её нет, а серверный дедуп по повторному идентификатору отправки живой пробой не проверялся и здесь не обещается.

## Ограничения и пробелы в доказательствах

Раздел честный. Часть протокола подтверждена живыми прогонами, часть только реверсом бандла веб-клиента, и это разные уровни уверенности.

Полигон живых проб один: чат с собой («Избранное», тип `notes`). Групповые чаты, чужие переписки и вложения на реальных данных за границы живого тестирования вынесены сознательно. Отправка живьём выполнялась один раз вручную и в непрерывной интеграции не повторяется.

Статусы ниже: **[live]** наблюдено в живом трафике, **[bundle]** снято с бандла веб-клиента, **[нет]** не установлено.

### Чего нет по решению (отложено)

- **Real-time нет.** Никаких подписок на живые события: новые сообщения, набор текста, прочтения, присутствие. Инструмент отвечает на запрос, а не слушает поток. Бота и автоответы на нём не построить.
- **Из записи есть только отправка текста.** Девять инструментов записи отложены: `send_file`, `edit_message`, `delete_message`, `vote_in_poll`, `set_reaction`, `mark_read`, `pin_message`, `join_to_thread`, `leave_thread`.
- **Упоминания не поддерживаются.** Форма упоминания во внутреннем событии не снята, поэтому `send_message` отправляет текст как есть.
- **Расшифровка вложений не реализована.** Файл сохраняется на диск таким, каким его отдал сервер, с пометкой `encrypted:true`.
- **Поиск по текстам сообщений платформой не поддерживается.** Это не отложенная работа, а отсутствующая возможность: ручки поиска не снято ни живьём, ни из бандла.
- **Авторизация только через профиль веб-клиента.** Прямого входа по логину и паролю нет, мульти-аккаунт не поддержан.

### Что не подтверждено живьём

- **Признак продолжения на странице треда.** У страницы чата признак наблюдён живьём (`has_more_events`), а страница треда живой пробой в этой итерации не читалась: в полигоне тредов нет. Поэтому `get_thread` при отсутствии признака по-прежнему несёт `form_status:"unconfirmed"`.
- **Связка адреса треда со стартовым сообщением.** Взята из бандла: на полигоне тредов нет, подтвердить или опровергнуть равенство было не на чем.
- **Файловая служба и расшифровка файла.** Адрес и параметр `key_id` из бандла, смысл `key_id` не установлен. Схема потокового шифра файла тоже из бандла и не реализована.
- **Опросы.** На полигоне их нет структурно: опрос нельзя завести в чате с собой. Форма опроса и признак опроса в сообщении из бандла.
- **Серверный дедуп по повторной отправке.** Клиентский идентификатор отправки есть и наблюдён живьём, а поведение сервера при повторе с тем же идентификатором не проверялось.
- **Точный срок жизни токена.** Обновление токена наблюдено живьём, но значение `expires_in` в момент реального обновления не снято.

### Границы доверия

| Утверждение | Статус | Источник или где проверено |
|---|---|---|
| Авторизация сокета своим клиентом на Node без браузера | [live] | Прогон собственного клиента на живой сессии |
| Первая попытка авторизации сокета иногда остаётся без ответа, нужен повтор | [live] | Два прогона подряд: первый без ответа, второй успешен. Отсюда `ws.authenticateAttempts` по умолчанию 2 |
| Полный список чатов запросом дельта-синхронизации с нижней границей 1970 | [live] | Полный базовый список получен собственным клиентом |
| Счётчики непрочитанного приезжают отдельным событием, а не полем чата | [live] | Живой ответ с массивом счётчиков по чатам |
| Чтение истории назад с лимитом и курсором пропуска до события | [live] | Живая страница истории полигона |
| Порядок элементов в ответе истории | [live] | Сервер отдаёт от новых к старым; порядок им не обещан, поэтому страница всё равно сортируется на нашей стороне |
| Курсор истории: адрес в поле `sync_id`, `skip_to_sync_id_event` булев флаг | [live] | Кадр с адресом внутри самого флага сервер отвергает |
| Включающая семантика курсора пропуска | [live] | Событие курсора приезжает в странице; наружу граница объявлена исключающей, событие выбрасывается явно |
| Признак продолжения `has_more` | [live] | Приходит полем `has_more_events` рядом с `history` и `generated_at` |
| Расшифровка событий: обёртка контент-ключа и AEAD с привязкой к паре чата и события, ключи из профиля, подбор по идентификатору публичного ключа | [live] | Входящее живое сообщение расшифровано собственным кодом |
| Round-trip отправки: обёртка контент-ключа на каждый ключ чата через службу ключей, обёртка одним ключом отправителя, подпись над base64-строкой нагрузки | [live] | Отправка своим кодом принята сервером, сообщение прочитано обратно, тело совпало |
| В ключах полигона два ключа получателя, обёртка идёт одним ключом отправителя | [live] | Отправка с обёрткой не на те ключи отвергается сервером |
| Роль второго ключа в наборе ключей чата | [нет] | На отправку не влияет: набор берётся из объекта чата |
| Серверный дедуп по повторному идентификатору отправки | [нет] | Повтор с тем же идентификатором не проверялся |

### Открытые долги

| Долг | Что нужно, чтобы закрыть |
|---|---|
| Обновление токена только реактивное, проактивного TTL нет | Снять точное значение срока жизни токена: поймать тело ответа обновления в момент реального обновления (протухший профиль либо окно наблюдения длиннее половины срока жизни) |
| Прямое обновление токена из Node не используется | Прогнать запрос обновления из Node и убедиться, что новые cookie корректно ложатся обратно в профиль |
| Признак продолжения у страницы треда не наблюдён | Прочитать живьём страницу треда: в полигоне тредов нет, нужен чат с тредом |
| Серверный дедуп по повторной отправке не проверен | Повторить отправку с тем же клиентским идентификатором и посмотреть, создаётся ли второе сообщение |
| Форма опроса на групповом чате не снята | Живая проба в групповом чате: прочитать сообщение с опросом и сверить состав полей с формой из бандла |
| Загрузка и расшифровка вложения не отрабатывались живьём | Скачать реальное вложение и снять разметку потокового шифра, попутно разобрав смысл параметра `key_id` |
| Смысл параметра `key_id` файловой службы не установлен | Тот же живой прогон загрузки |
| Упоминания не поддерживаются | Снять форму упоминания во внутреннем событии и научить отправку её собирать |
| Поиск людей только по контактам с личным чатом | Найти серверный справочник людей либо зафиксировать его отсутствие как свойство платформы |
| Связка треда и стартового сообщения взята из бандла | Живая проба: создать тред и сверить его адрес с адресом стартового сообщения |
| Роль второго ключа в наборе ключей чата не установлена | Разобрать, какому устройству или сессии принадлежит ключ |
| Девять инструментов записи отложены | Отдельная итерация: `send_file`, `edit_message`, `delete_message`, `vote_in_poll`, `set_reaction`, `mark_read`, `pin_message`, `join_to_thread`, `leave_thread` |
| Протокол может уехать вместе с релизом веб-клиента | Держать протокольные константы в секции `protocol` конфига, чтобы часть поломок чинилась без правки кода |

## Разработка

```bash
npm ci
npm run typecheck   # tsc вместе с тестами
npm test            # vitest
npm run build       # tsc, сборка в dist
```

Кроме обычных тестов прогон включает греп-гейт наблюдаемости: он читает дерево исходников и проверяет свойства, которые нельзя проверить вызовом. В stdout не пишет никто, кроме логгера и точки входа; имена событий и топиков живут только в нижних слоях и не поднимаются в инструменты; в тестах нет пропущенных, единственных и недописанных мест; комментарии только блочные; в исходниках нет длинного тире и двойного дефиса. Правило про исходник обязано падать до сборки, иначе оно опаздывает ровно на ту сборку, в которой нарушение уже уехало.

### Живой smoke-тест

Живой прогон ходит на реальную учётную запись и по умолчанию пропускается. Запуск явный:

```bash
CLOUDS_MESSENGER_MCP_E2E=1 \
CLOUDS_MESSENGER_MCP_PROFILE_DIR=~/.config/clouds-messenger-mcp/profile \
CLOUDS_MESSENGER_MCP_E2E_CHAT=<uuid чата> \
npx vitest run tests/e2e/liveSmoke.test.ts
```

Без переменной `CLOUDS_MESSENGER_MCP_E2E` набор пропускается целиком, поэтому обычный `npm test` и непрерывная интеграция его не запускают. Первый запуск на чистой машине требует браузера: `npx playwright install chromium`.

Он намеренно ТОЛЬКО читает: ничего не отправляет и ничего не качает, чтобы его можно было безопасно гонять повторно. Полигон один, чат с собой; отправка живьём выполняется вручную и в непрерывной интеграции не повторяется. Ассерты идут по числам и признакам: живые данные не попадают ни в вывод, ни в диагностику падений.
